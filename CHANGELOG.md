# Changelog

## 0.25.0

**How this PR was decided** now reads what a long agent session did for the PR: the full-suite runs it sent to logs, the failures it re-ran, the verification note it wrote, and the PR in another repository the work was split with. The Intent and the model come from the session that did the commit's work. Replayed on the 29 checkpointed PRs of a web-app repository from one week, briefs with the section went from 18 to 22 and rows from 29 to 40 (11 verification notes), and rows naming only the runner went from 8 to 3. Every changed row on 12 of those PRs was checked by hand against its transcript.

- **Intent and model:** Entire attaches every session live in the checkout. The session that did the commit's work is now picked by the strongest evidence first: it ran the `git commit` that made the commit (the short sha the call printed starts the commit's; for a quiet call, the message its command shows is the commit's whole subject, a squash's ` (#123)` aside, never a prefix of it; two sessions showing the same message: the one whose commit ran where it worked on the files); Entire saw it write a committed file and it worked on one by its full repo path; Entire saw it write one; it worked on one by its full repo path; by basename only. A session that writes through a shell leaves Entire's list of written files empty, so that list alone never rules a session out. The model now comes from that session, not always from session 0. On a web-app PR, an unrelated session that grepped another folder's `types.ts` matched the commit's `types.ts` by basename, and its model and first line became the commit's. Inside a tier, the session that wrote the most of the commit's files comes first. The turn now starts at the person's prompt before the first full-path work at the commit's checkout (the checkout of the last such work). When the turn committed another PR first, the turn starts at the agent's last line before this commit's work. In the replay, Intent cells that had opened with another ticket's line ("The popup is…", "I'll find the design skill's files…") now name their own ticket, and four headers that named the wrong model now match the commit's `Co-authored-by`.
- **Decisions follow the same sessions:** the session that made the commit, and any that worked at the checkout it was made in, give the decisions; with no session shown making it, those Entire saw write the commit's files, else those that worked on them by path. A session that only ran a test the commit changed, in its own worktree, names the file by its repo path too; on one PR that gave three rows from another ticket's session, and on three others a question asked about another PR.
- **Logs:** a test run whose output went to a file (`vitest run > full.log 2>&1; echo done`) takes the output of the first later call that read that file and shows the runner's summary, before anything writes the file again. The file is matched by its whole name (`web-full.log` is not `full.log`). Before, both of that PR's full-suite runs had no outcome. A redirect is now removed whole before a run's targets are read, so `> full.log` is no longer read as a test file and a redirected whole-suite run counts as the whole suite.
- **Failures and re-runs:** runs are grouped by what they ran (runner and targets) and where: a run with no `cd` of its own joins one that has one, and two different known directories never share a group or close each other; a pass in another directory does not keep a failure from being called its last run either. So a pass of one file no longer closes a failure of another under one runner name. On that PR, an unrelated file's pass had closed the folder run's failure. A failure closes when later runs together cover the files its output lists failing: vitest's and jest's `FAIL <file>` lines when they match the summary's count of failed files, pytest's `FAILED <file>::<test>` lines when the distinct tests match the closing line's `N failed`. With no count to check, or a list a pipe cut short, the files are unknown. Only a run fed from a pipe (`xargs vitest run`) that counts exactly as many files as were failing, all of them among them, is a re-run of those files; a narrowed run (`-t`, a bare name) that happens to count as many never is. A whole-suite failure says how many files failed and whether none of them is in the change: "`vitest` (whole suite) failed in 15 files, none in this change" → **re-ran them**, then they passed, or → **committed**: none of the failing files is in this change. Failing files the change carries are named, even from a folder run. A path is read from the run's own directory when its `cd` is known (relative to the repo root, or the changed file an absolute path ends with); with it unknown, a path two changed files both end with names neither and is not called outside the change.
- **Verification:** a Markdown note the change carries, whose name has `verif` in it and that the session wrote (`Write`, `Edit`, a heredoc), gives a row from its status as the commit holds it: verified the change end to end → **PASS**, recorded in the note's path. The front matter's `status:` line wins; without one, the body's status lines must all agree, so "Unit: PASS" over "E2E: FAIL" gives no row. A note edited to FAIL after it was first written reads FAIL; a note first committed in a later commit reads what the session wrote. Notes written through a heredoc (`cat > note.md <<'EOF'`) now count, for design notes weighing alternatives too.
- **Linked PRs:** a PR in another repository that the PR body or a commit names (`owner/name#123` or its link, at most 5) leads the table: merged, open or closed, its review threads resolved, and GitHub's review decision. The Action reads them with the new `linked-token` input. It defaults to `github-token`, which reads only this repository, so the row says "not readable with this token" rather than vanish. A number the repository resolves to no pull request (an issue, a branch name like `release/v2#3`) is dropped. GitHub returns at most 100 review threads; past that the row says "of the first 100 of 150". The new `blastline linked-refs` command prints the references, and `brief --linked <file>` takes the lookups.
- **Late transcripts:** Entire can snapshot a transcript before the commit's own `git commit` is logged. If the last commit it shows was made in another repository's checkout, the decision window now uses the checkout where the commit's own files were last worked on by their path. Before, that window was empty. With no commit shown at all, nothing is read, as before.
- **Calls made elsewhere:** a call that `cd`s (or `pushd`es, `git -C`s) to an absolute path outside the change's checkouts, and never comes back, is left out of the decision window even when the agent was at home just before it. Before, a whole record counted as home when the agent was home before any of its calls.
- **Directories:** a run with no `cd` of its own runs wherever the shell already stood, so it can be closed by a later run that `cd`s first. On one PR, a failing contract test was later passed by a run that began with `cd` into the worktree, but was reported as fixed only by accident (an unrelated pass under the same runner name).
- **Speed:** the full-path match reads each command's words once against a set of the change's paths, and the per-file patterns that remain are tried only on commands that contain the path. A 15,000-call session naming 400 changed files went from about 12 seconds to about 1, and a command holding a 10 KB run of slashes takes milliseconds.
- **Claims:** a folder the PR body names (`openspec/changes/x/`) is found in the changed paths inside it. Before, it was called a phantom change.

## 0.24.1

A test that failed, then passed in a broader run, now shows in **How this PR was decided**.

- A failing run that names test files is closed by a later passing run of the same runner that covers them: the whole suite, the same files, or a folder holding them. The row says "failed, then passed". Before, the broader pass was keyed differently, so it only stopped the failure from being called the last word, and the row was dropped. On a real web-app PR whose new tests failed twice and then passed in a run over their folder, the section was empty; it now shows both runs. A later pass on unrelated files still closes nothing. Neither does a pass from another directory, or one narrowed by a test-name filter, a project, a config or a bare name (`-t`, `--testNamePattern`, `--project`, `--config`, `-k`, `-run`, a file-name filter). Such a pass doesn't close a failure even under the same key. Flags that only report, time or schedule (`--coverage`, `--testTimeout=`, `--maxWorkers=`, …) don't narrow. A pass in the same transcript record also keeps a failure from being called its last run, since calls in one record have no known order.

## 0.24.0

The decisions section becomes the brief's lead: **How this PR was decided**, a table of what happened, what was decided and the commit as evidence. It now reads questions the agent asked and independent reviews, and it keeps work an agent carried to the commit's worktree as a patch.

- The section is a table and comes first, before "What each commit did". Each row is built from fixed labels, outcomes and the change's own paths. For example: `vitest` failed → **fixed**, then it passed; asked you a question → **you chose the recommended option 1 of 3**; asked an independent reviewer (`code-reviewer`) → **changes requested**. No transcript text is quoted.
- **Questions:** an `AskUserQuestion` call says which option the person picked, by position only (several on a multi-select question), or that they answered in their own words. Neither the question nor any label is quoted, and when two labels are alike no position is claimed.
- **Reviews:** an `Agent`/`Task` call whose type or description names a review or critic as a word ("critical" and "preview" don't count). The verdict is read only where a reviewer states one: a `Verdict` line or the line after a `Verdict` heading, a line that opens with `APPROVE`, `CHANGES REQUESTED`, `BLOCKED` or `READY TO MERGE`, or a check lane's `result: findings|no findings`. Blocking words win, and "not APPROVED" in a sentence is nothing. It is read from the call's result, from a later task notification, or from the reviewer's last message in the subagent transcript Entire keeps under `tasks/`. Otherwise the row says "verdict not recorded". Rounds that read alike stay separate rows, told apart by their tool call.
- **Carried work:** when an agent fixes something in one checkout or worktree and carries it to the commit's as a patch (`git diff > <file>` there, `git apply <file>` here), the first one's work counts too, from after its own last commit, so the PR it shipped on its own stays out. A sibling worktree with no such hand-off never counts. A variable can build on one assigned before it (`NEW="$REPO/x"`), and the "left the repo" and "back at the root" checks read assigned variables (`W=/repo; cd "$W"`).
- **Probes:** a test run against swapped-in code is skipped whether the old code is written over the same path before the run (`git show <ref>:<path> > <path>`, a bare `git stash`, `git apply -R`) or the fix is copied back after it, including from a loop's `do cp`. Saving an old copy elsewhere, `git stash pop` and a `2>` redirect are ordinary steps.
- **Replay:** on 100 checkpointed web-app commits, briefs with a decision went from 21 to 22, plus review rows on three more, and every new or changed line was checked by hand against its transcript. On the web-app PR whose fix was carried as a patch, the brief now shows its failed-then-passed contract test.

## 0.23.1

Two fixes: a data file could select zero tests, and a PR's Intent could open with another session's work.

- A changed data file whose walk reaches no test now runs the full suite instead of selecting zero tests. "Data" means a file that isn't in one of the languages CGraph parses as code (C, C++, C#, Apex, Go, Rust, Groovy, Java, JavaScript, Kotlin, Delphi, Python, Ruby, Scala, TypeScript), such as SQL, Cypher, GraphQL, Protobuf, OpenAPI and XML. The graph records no reads of data by code, so a walk that finds no test is not evidence that no test reads the file. That holds whether nothing points at the file's nodes, only another migration's foreign key does, or only untested code does. On a TypeScript service, a one-line edit to each of five migrations selected 0 tests before and runs the full suite now; migrations were masked while their journal file had no graph node, and exposed once the journal folder was ignored. A data file whose walk reaches tests (a table a model uses) keeps its subset, and a code file nothing depends on still selects zero tests. The comment says the file "reaches no test in the graph" (`unreached` on the reason), not that it has no node.
- The Intent cell's narration and the "Ran before push" commands come only from the sessions that worked on the commit's files, as the prompt already did. Entire attaches every session live in the checkout when a commit is made. On one web-app PR, ten sessions were attached. The Intent opened with a call-summary session's first line, and 30 test commands came from other tasks. Now it shows the working session's own words and its 2 commands. With no session working on the files, every session still counts.

## 0.23.0

"What the agent decided" finds test outcomes, edits and subagents the way agents actually work. Replayed on 96 checkpointed commits of a web-app repository since 2026-09-20, the section had a line for 1 of them before (a design note) and for 20 after: 13 with runs that failed and then passed, 6 commits made right after a failing run with no pass, and 4 with design notes weighing alternatives (one commit can have several).

- A test run's outcome comes from the runner's own summary in its output when there is one (vitest's `Test Files`, `Tests` and `Errors` lines, jest's `Test Suites:` and `Tests:`, pytest's closing `===` line), read and never shown. Until now only a bare run's exit status counted, and agents almost always pipe a run (`vitest … 2>&1 | tail`), so the rule almost never fired. A bare run that exits non-zero failed, whatever its summary says (vitest exits 1 on a file that fails to import with every collected test passing). A bare run with no summary still counts by its status, unless the harness never ran it (a denied permission). cargo's `test result:` and go's `ok`/`FAIL` lines only ever say a run failed: a pipe can cut off the failing package's line.
- A command counts as one run only when it holds exactly one runner in command position. A run followed by a step that puts files back (`cp`, `mv`, `git apply`/`checkout`/`restore`/`stash`, `patch`) is a probe against swapped-in code, not an outcome, and is skipped. A file named through a variable the command assigns (`T="src/a.test.ts"; vitest run "$T"`) still counts.
- A test line names test files only when everything the run targets is a test file the change carries. A run over a folder or another file may have failed there, and a config file a flag points at is not what ran, so those name only the runner.
- "Failed on its last run" is not said when the same runner passed later in the window, on any files.
- The repo root also comes from Bash: a call that runs in a known directory and names one of the change's files by its repo path. The shell's directory is followed across calls through absolute and relative `cd`/`pushd` (`builtin cd` too, redirects aside), with a variable the same command assigns substituted (`WT=/repo; cd "$WT"`) and `cd "$PWD"` staying put; any other move (`popd`, a bare `cd`, one it cannot read) makes it unknown. Agents that edit through scripts (`python3 - <<EOF`, `cat > file`) now have a root. Temp folders are never a root.
- When edits name more than one checkout of the same layout, the root is the directory the transcript's last `git commit` ran in (the commit the checkpoint was written for), when it is one of them. Before, two roots meant nothing was read.
- Entire 0.11.5 keeps a subagent's transcript under `tasks/<tool_use_id>/agent-<id>.jsonl` when its hooks see the subagent start. Its tool calls are read inside the turn that started the subagent, right after the `Agent` call, for decisions only: the ask, narration and test commands still come from the parent.

## 0.22.0

The brief's blast radius says why each reached file depends on the change.

- `parseChangeContext` keeps `cgraph change-context`'s `impacts[]`: each reached node's repo path and CGraph's witness links (source, relation, target) from it to a changed node. Until now only the `omitted` counters were read.
- Under "Blast radius by changed file", each reached file names the chain CGraph kept to a node in that changed file: `src/a.ts (imports src/b.ts, which imports it)`, `use (src/c.ts, calls run in src/b.ts, which calls parse)`, `load (web/client.ts, uses GET /items, which is handled by listItems)`. The changed end reads "it" when it is the file itself. A step names a symbol or endpoint by its label, with its file when that differs from the step before; a file serving an endpoint reads "served in" that file. CGraph keeps one chain per node of the reached file; the shortest wins, and on a tie one starting at a symbol, which the reason then names (`aa, bb, cc, +1 (src/x.ts, zz calls parse)`) unless it is the one symbol shown.
- A reached file shows no reason when CGraph's witness for it leads to another changed file (CGraph keeps one witness per node), or when the budget shed it.
- The plain comment (`blastline comment`) has no change-context and is unchanged.

## 0.21.0

The Action installs CGraph bin-v0.9.5 by default (was bin-v0.5.0), and the brief stops treating CGraph's contract nodes as code.

- `cgraph-version` defaults to `bin-v0.9.5`. Replayed on 46 merged PRs and 5 direct commits across five repositories (three TypeScript services, a Kotlin/Spring service and its web client), with a base and head graph per change and each repository's own ignore list: no test bin-v0.5.0 selected is dropped and no verdict changes kind. bin-v0.9.5 adds tests on three changes in the Kotlin service's repository. The clearest is cross-service: a commit to a Kotlin controller now selects the two TypeScript end-to-end specs that call its endpoint, where bin-v0.5.0 selected none. A token-claims change reaches the tests that read those claims, and a JavaScript gateway change gains one test through a wrong edge both versions already had. Graph builds take about a second longer (median 4.9 s against 6.0 s on one service and 8.7 s against 9.7 s on another, built side by side).
- Config that Spring loads by convention (`application*.yml`) gets graph nodes in bin-v0.9.5, but still runs the full suite, as 0.19.0 made it do whatever the graph holds; only the reason now says `(convention)`.
- bin-v0.9.5 links an ORM model to its migration's table, so a one-line migration change can now select most of a suite (0 tests before, 213 of 328 on one service). That is more tests run, never fewer, and the `--max-selected-fraction` fail-open catches the widest.
- Contract nodes (`<kind>:<name>`: endpoints, tables, headers, env variables, claims, and `cgraph seam`'s schemas and services, also behind a fused graph's `<service>::` prefix) are seams the walk crosses, not code (`isContract` in `src/graph.ts`, following CGraph's `contract_kind_of`). `check callers` never lists one, so removing an ORM model whose migration table remains is no longer refuted by the table. The blast list and reached files leave them out, so the "Downstream code" count, the owners scan and the overlap with other open PRs are code only. A test file a contract was minted in still counts, so selection is unchanged (the same replay matches before and after, 102 of 102 runs).
- A changed or removed symbol's callers take their repo path from the graph's `source_file`, less the repository root the symbol's own file gives. CGraph labels a file by its parent folder and name only, so a caller nested deeper got a wrong path, and a caller in a file the diff changed could be counted as untouched; guessing the root from the changed paths also went wrong where the same relative path sits at two depths.
- `blastline tests --json` (and every other command) printed only the first 64 KiB when its stdout was a pipe: on a pipe Node writes asynchronously and `process.exit` dropped the rest. The CLI now makes stdout blocking, except for `blastline mcp`. The Action wrote to a file and was not affected.

## 0.20.0

The brief says what the agent did across the PR that the diff cannot show: tests it made pass, work it undid, alternatives it weighed.

- A new section, **What the agent decided**, lists at most 8 lines, each with its kind and the commit whose checkpoint holds it, in session order. `src/decisions.ts` reads them from the compact transcript, without a model: a test runner and the test files the change carries that failed and then passed or whose last run failed, reverts, and design notes the change adds that weigh alternatives.
- No free text is quoted, neither what a person typed nor what the agent wrote. Every line is built from a fixed label, a test runner's name and the change's own repo paths, so nothing private can leave the ref however a session went. Seven review rounds of word filters each found a new way for free text to carry a password, a name or another repo's details, and each fix left less to show, so the section carries no free text at all.
- A test is read by its runner, the test files the change carries and its call's status, only for a bare run (a script, a chain or a pipe sets the status, so it is not read); a revert by a fixed label such as `git revert`; design notes by their repo path, and only when the change carries them. Tool output and commands never leave the ref. The README's allowlist lists the new lines.
- Only turns that hold a tool call working on one of the PR's files at this repo's root are read, from the commit's own turn on, inside what the previous checkpoint of the session left unread. The root is the one every edit to a file inside a folder agrees on; with none, or two (another checkout of the same layout), nothing is read. A command counts only by the absolute path, since the shell keeps its directory between calls. What the agent does while away from the repo is skipped: it starts away, leaves on an edit, read or search outside the root, a `cd`, `pushd` or `git -C` elsewhere, a `../` or `$VAR/` path, or an absolute path outside the root (temp and device paths, and quoted routes such as `'/api/v1'`, aside), and is back on work at the root or a `cd` to it, across turns. A revert commit whose turn names none of its files shows no revert.
- On four real web-app PRs the section shows design notes weighing alternatives on one; the other three show no section.

A blocking Stop hook sends "Stop hook feedback:" after every reply, so each commit's turn began at its last reply and the cell showed one response of the session. Interrupt markers, compaction summaries and usage-limit notices are harness text too, and an attached image's caption is skipped. On a web app's checkpoint branch (272 transcripts) Stop hook feedback alone opened 1,532 user records.

The line comes from a text block a person typed, never from one the harness appended to the turn. With several sessions, the one that worked on the commit's files supplies it. When no tool call works on the files, the last prompt since the previous checkpoint is the ask; when nothing bounds the transcript either, none is guessed and `prompt.txt` is used as before. `brief --local` filters its line the same way.
- The README's privacy allowlist names the new source: that one line of the turn's opening prompt in `transcript.jsonl` leaves the ref; every other prompt line still does not.

## 0.18.0

A `package.json` change that only adds scripts no longer runs the full suite.

- `inertScriptAddition` in `src/manifest.ts` reads a changed manifest at the range's base and head. It qualifies when the text is unchanged apart from whitespace, or when every key outside `"scripts"` is unchanged in value and order (Node resolves `exports` conditions and Jest applies `moduleNameMapper` in order), every existing script is unchanged and keeps its order, and each new script is neither a lifecycle or host hook (`pre*`, `post*`, `prepare`, `test`, `build`, `vercel-build`, ...) nor run by anything opaque: named by a non-code file outside Markdown (a workflow, a CI helper, a pre-commit hook, an existing script, a line keyed by it), or matched by a pattern -- its first segment with a wildcard, anchor or open string (`run-s "test:*"`, `/^test:/`, `"test:" + kind`), its last with a leading wildcard (`*:e2e`), or a pattern-runner command (`run-s`, `run-p`, `npm-run-all`, `turbo`, `nx`, `lerna`, `pnpm`, `yarn`, ..., by path or with a version) with any `*`. Pattern matches in files nothing runs from (`.gitignore`, `CODEOWNERS`, lockfiles) are skipped; literal mentions never are.
- A script run whose name is decided at run time -- a placeholder (`$`, `{`, `:::`, `%VAR%`, `!VAR!`, a backtick substitution) or pnpm `/regex/` anywhere in a command after a `run`/`run-script` that a package manager or a variable standing for one precedes (so a flag's value cannot hide it, and `gh workflow run` or `docker run` do not count), or a `run \` continued on the next line, or names piped into a package manager by `xargs` or `parallel` (`pnpm -r run "$s"`, `"$npm_execpath" run $s`, `${PM:-npm} run "$s"`, `xargs -I{} npm run {}`, `npm run {{suite}}`, `npm run ${{ matrix.app }}:e2e`), the same as a package manager's first argument, or any placeholder given to a script tool -- or a line listing the manifest's scripts (`.scripts | keys`, `Object.keys(pkg.scripts)`) may pick up any new script: outside code it fails the manifest open, in code it is walked. A file run, even a computed one (`bun run scripts/x.ts --base "$SHA"`, `bun run "scripts/$TOOL.ts"`), is not one; `docker run $IMAGE` is, which errs wide.
- A comment naming a new script is ignored; a code line naming it or building its name is walked like a changed line, so its tests are selected. A qualifying manifest with no such code is skipped with its own row ("only adds scripts nothing runs: …"). Everything else fails open as before, including a supplied diff (judged as supplied even when a range is also given), a three-dot range, and an added, deleted or renamed manifest.
- On a real web-app PR adding two scripts beside the tool they run, the run goes from all 395 test files to 1. Replayed over the 30 recorded full-suite PRs: all 30 verdicts unchanged (their manifest changes are dependency bumps or script edits).
- Review of this change found, and it now refuses: CI running scripts through a matrix variable or a shell loop over the scripts list, CI helper scripts and pre-commit hooks that run a new script, key-order changes passed off as formatting, a supplied diff judged by the range beside it, pattern runners by suffix glob, by path, by version or across a continuation line, code concatenating or regex-filtering the name, and a script named `constructor` skipping the check.

## 0.17.1

The reader advice names the readers, not every module beside them.

- A folder mention is followed segment by segment while it agrees with the file's path, and stops counting the moment it turns off: `@/lib/upload/grid` no longer counts as a way to `lib/upload/testdata/x.csv`. Before, only the first segment after the folder was checked, so every module importing a sibling was listed; on a real web-app PR a new test fixture listed 36 readers reaching 26 tests, now 13 reaching 11, with the test that loads it first.
- Readers are ordered by evidence (named outright, then Spring profile and context, then path pieces), and the table shows the caveat that can hide tests (config that changes how tests run, a profile activated elsewhere) before noise.
- A template or glob segment (`${kind}`, `*`) stands for one path component and the comparison continues past it; only `**` matches any depth. Before, any template counted at once, so every route under a Next.js `[uuid]` folder was a reader: on an app-router fixture, 227 readers become 27.
- Whether a file walks directories is read only when a mention could count: never for a bare word (`new` in `new Map()`). Before, every file mentioning a parent folder was read: 5,000 `git show` calls and 32 seconds on a 5,000-file probe that found nothing; on the app-router fixture, 1,478 reads and 14 seconds become 235 and 3.
- The shown caveat puts a truncated walk ("exceeded the traversal budget", "go deeper than") with the ones that can hide tests. `\bglob` no longer matches `globalThis`. `.gitignore` ignores a symlinked `node_modules`.

## 0.17.0

Under a full-suite verdict, the comment says which code reads each unmapped file and which tests those readers reach. Advice only: the verdict never changes.

- `resolveReferences` in `src/references.ts` finds readers at the range's head: a non-comment line naming the file (directives such as `#include`, `//go:embed`, `/// <reference>` and Rust `#[...]` count); a piece a path can be built from (the stem in quotes, the file's folder used as a path, a higher folder in a file that walks directories, a directory walk over its extension); and, in a Spring repository, context tests for `application.yml` or code naming, templating or activating the profile for `application-<p>.yml`, with subclasses and meta-annotated classes followed. A non-code reader is followed to the code that names it; lockfiles and repository metadata (`.github/dependabot.yml`, `CODEOWNERS`) never read anything.
- `unmapped-file` gains `readers`, `readerTests` (the test files the readers reach, each reader seeded at the innermost symbol around its naming lines via `seedLines`, now shared with changed lines) and `caveats` (build or CI config mentioning it, activation by expression, a reader reaching no test, a non-code reader nothing runs, no code reads it).
- The unmapped block renders a table per file (readers, tests reached, first caveat) and the reached tests behind a fold.
- A first version let these readers replace the full suite. An independent review built probes where it silently dropped real tests (pytest fixtures, `@SpringBootTest` base classes and meta-annotations, paths built from a stem, `os.ReadDir`, profiles activated by constants), and the version strict enough to be safe vouched for none of 30 real full-suite PRs. So it ships as advice. Replayed over those 30 PRs: verdicts identical to 0.16.0 on all 30; 17 of the 29 full-suite PRs get a reader table.
